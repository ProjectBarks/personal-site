there has been a lot of hype around token saving tools for llms like [rtk](https://github.com/rtk-ai/rtk), [headroom](https://headroom-docs.vercel.app/docs), and [ponytail](https://github.com/DietrichGebert/ponytail). everytime i read about these i wonder the same question, "do these actually work?".

i really haven't seen extensive a/b testing from these tools nor do these optimizations make sense in an efficent market. i'm not sure a good name for this but i'll just it the "platform envelopment paradox" why would anthropic or openai not just adopt these optimizations internally and forward a chunk of the savings to you, headroom/rtk/ponytail all save tokens but i'd imagine most engineers at these labs are looking for simple ways to save compute all day. either way it just feels in this case any major token optimization which could be lifted to their platform will/would be. i wanted to go ahead and actually evaluate these in a much more controlled manner. funny enough jetbrains already had already [tested](https://blog.jetbrains.com/ai/2026/07/rtk-claude-code-token-savings/) rtk and found it increased costs, so i wanted to apply the same tests for headroom.

## the plan

most of headrooms [benchmarks](https://headroom-docs.vercel.app/docs/benchmarks) compare relative to itself. when running locally you see numbers saying how you are saving so much $$$ when we can't say how this non-deteministic entropy hole would act without headroom.

to compare i would use [harbor](https://www.harborframework.com/) with the Sr SWE bench with headroom in a variety of configurations. i would run claude multiple times and compare it to claude with headroom. running this required me to spin up a bunch of vm's with a anthropic api key (no subscription pricing) so i decided to sample 25 test cases which would favor headroom.

## what i found

headroom has two modes token mode, and cache mode. token mode will rewrite history and cache tokens mid transcript, cache mode will only rewrite the newest part of the transcript. the token mode cut total input tokens from 215M to 132M across the arm. that part works exactly as advertised. *yay*

## a cache read costs a tenth of a fresh token

here is the most important thing to understand of llm providers. all tokens are not billed the same!

with provider prompt caching, tokens are not fungible. at published Sonnet rates,
fresh input runs $3.00 per million and a cache read runs $0.30 per million. a cache
read is a tenth the price. an agent loop that keeps appending to a stable prefix is
close to the ideal case for this: on the baseline arm, roughly 98% of prompt tokens
were cache reads.

now consider what compression does mechanically. it rewrites history. rewriting
history changes the prefix. changing the prefix invalidates the cache.

the control arm busted the provider cache 14 times across 25 tasks. the compression
busted it 123 times. cache-read reuse per write token fell from 38:1 to 11:1.
compression removed tokens, and in the process pushed six million *other* tokens out
of the cache and into full-price billing.

the value of the lost cache discount came out within
a dollar or two of the value of the compression savings. you are trading
tokens at $0.30 for the privilege of sending fewer tokens at $3.00.

## so then what savings is headroom claiming

headroom reports its own savings, and it reported saving real money on this run. it
overstated by roughly 1.9x. the mechanism is worth describing precisely, because it
is a general failure mode and not headroom's alone.

<ClaimedVsRealized />

the savings metric credits every removed token at a flat rate, around $2.00 per
million. but the tokens it removes on this workload were cache reads. the
cache-weighted price actually paid was about $0.79 per million. crediting a $2.00
saving for dropping a token that cost $0.79 is most of the gap.

the rest of the gap is what the metric does not do at all: it never subtracts the
cache reuse the compression destroyed. it counts the tokens it removed. it does not
count the tokens it knocked out of the cache somewhere else in the loop.

per task, the meter would happily report a saving on trials that came out more
expensive than baseline. that is the tell. a savings number that cannot go negative
is not measuring savings, it is measuring activity.

## some good things; it did not make the agent worse

solve rates were flat: 5 of 25 with compression, 4 for baseline, 4 for the control.
i had subagents read the full session transcripts for every task where the arms
disagreed, side by side, rather than trusting the aggregate.

the disagreements were model nondeterminism, not compression. where compression
"won," it won by spawning a research subagent, or by diagnosing the true root cause
while the baseline patched the wrong layer. none of the baseline runs showed the
symptoms compression is supposed to cure: no forgotten findings, no re-reading a file
it had already seen. the one hard regression turned out to be an infrastructure
cutoff mid-run, with the transcript ending on a credit-balance error and zero edits
made.

so compression matched the baseline's reasoning quality on 39% fewer input tokens.
that is a genuinely useful result. it is just not a cost result.

## the bottom line

headroom compressing agent history works, and on a cache-heavy workload it does not save money, because the cache discount you destroy is worth about as much as the tokens you remove.

before you trust a savings meter, check whether it prices removed tokens at what you
actually paid for them, and whether it can report a negative number at all. i would
like the industry to actually scrutinize these tools more and measure them in a more
scientifically rigourous way.

and run the A/A arm. the gap between "different" and "different from noise" was 17
percentage points here, which is more than large enough to have shipped the wrong
conclusion.

where compression still earns its place is when you are up against a context window
rather than a budget. matching baseline reasoning on 39% fewer tokens is real. it is
just a memory result wearing a cost result's clothes.
